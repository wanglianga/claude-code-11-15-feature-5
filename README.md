# 生鲜订货决策系统

面向叶菜/根茎等短保生鲜的门店订货系统。五个各自持有状态的模块靠**不可变版本**串联：

```
需求还原 → 分位预测 → 门店改量 → 收市复盘
   ↑__________（复盘决定哪些样本允许回流）__________|
                       ↳ 配送异常 → 应急订货推演（原订单不变）
```

- **需求还原**：按门店/品类/到货日，把缺货时段、断货标记、售罄时点、有货时段销售速率整成**截断观测样本**；
- **分位预测**：基于还原样本生成带**特征快照**的建议版本（临界分位 × 特征因子，向上取整到最小订货单位）；
- **门店改量**：店长只在该版本上改量、记原因码并确认订单；
- **收市复盘**：按订单版本归因实销、报损、缺货损失，决定哪些样本回流需求还原；
- **应急订货推演**：多种鲜货同时少送时，店长在浏览器内做**分批组合搜索**，在共享货源箱数与冷藏车容量约束下决定先补哪些商品；原确认订单保持不变。

> 领域前提：本系统经营叶菜/根茎等短保生鲜，属非限制经营品类；溯源与检验检疫信息由上游供应商随货提供，不在本系统建模范围内。

任一模块重算都不改写下游已确认的记录。

## 写死的取舍（口径中途不能换）

| 取舍 | 规则 | 代价/后果 |
| --- | --- | --- |
| 训练目标 | **不直接拿实销当需求**。缺货日实销被货架截断，先还原成截断观测（有货时段速率 × 全天营业时长）再建模 | 门店必须回传断货标记；标记缺失时页面只能**降级为保守估计**（实销为需求下界，不外推） |
| 复盘基准 | 复盘以**观测需求**（还原后需求）而非实销为归因基准，与训练口径一致 | 口径选定后中途不能换 |
| 建议量 | 临界分位 **τ = Cu/(Cu+Co)**（Cu=缺货单位损失含客流损失，Co=报损单位成本）。叶菜默认 8/2→**高分位 0.8**，根茎 2/2→**中位 0.5**；同品类不同门店允许覆盖（cost_params） | 不用期望值给数：期望掩盖尾部风险；单价比标定错会让历史订单损耗归因整体偏移，故 Cu/Co 随版本快照固化 |
| 取整 | 建议量**向上取整到最小订货单位**的整数倍 | 规则写入版本快照 `rounding=ceil_to_min_order_unit` |
| 版本 | 建议版本**不可变**：促销取消/降温/配送延误触发重算只产生新修订版本；店长已确认的订单版本原样保留，复盘按当时版本归因 | 历史版本只读可查 |
| 并发 | 店长确认与总部修订同时落库 → **按落库先后裁定**，另一方收到 409 冲突提示；同一到货日重复提交按**幂等键**并成一张建议表 | 数据库行锁 + 幂等键唯一约束保证 |
| 账实不符 | 库存与盘点对不上**以盘点为准**并留差异记录；**差异批次从训练样本剔除** | 否则系统库存会把需求还原污染掉 |
| 报损补录 | 次日补录的报损单落在窗口内（营业日次日 12:00 前）才触发**结转重算**；过窗的单独存档并说明出处 | 当日已锁定的建议量保持原样 |

## 技术栈

- 前端：React 18 + TypeScript + Vite + Zustand（三级筛选与建议表草稿状态）+ React Router
- 后端：Node.js 22 + Express + TypeScript + PostgreSQL 18（事务/行锁/唯一约束）
- 测试：Vitest + Supertest + Testing Library（server 33 项 / web 16 项）

## 应急订货推演（配送异常）

场景：**多种鲜货同时少送**，店长要在有限的货源箱数与冷藏车空间之间决定先补哪些商品。

| 取舍 | 规则 |
| --- | --- |
| 逐时缺口 | 分时需求按品类曲线摊到各销售小时；缺口 = 该小时需求 − 原单实际到货（订货量 × (1 − 少送比例)）− 应急货源 / 已到货回执（按各自到货时刻铺开） |
| 原单晚到 | 只有迟到时刻之后可售，早段缺口变大；页面重新提示应急单是否需要取消（已确认单提示先取消再重算） |
| 整箱分配 | 一箱覆盖份数 = 每箱份数 × 替代比例；替代货源补的是**目标商品**缺口，同一缺口不会被原商品与替代货源重复计数 |
| 同一批货 | 一个方案是一组货源箱数决策，每箱只出现一次；同一推演会话至多一张待确认/已确认应急单（部分唯一索引保证） |
| 共享车辆 | 每个车次（AM/MID/PM/EVE）最多 `maxVehiclesPerSlot` 辆，单车有重量上限与冷藏容积上限；多订一箱超出缺口通常只会增加报损，故搜索把每货源箱数上界收紧到 ⌈缺口份数 / 每箱覆盖⌉（替代/迟到货源可能仍需多订，由目标函数自身取舍） |
| 目标 | 缺货损失（按商品优先级加权 × Cu）+ 剩余鲜货报损（× Co）+ 同车合并后的车次运费 |
| 最优 vs 可行 | 按到达车次分批搜索；全部枚举完毕才标「已穷尽搜索」；达到节点/时间上限则只标「已找到的可行方案」，**不能标成最优** |
| 对照下界 | 页面同时显示「忽略共享限制时的最低成本」（各商品独立最优 + 理想合并装车），证明逐件挑最便宜会争用同一车次 |
| 三种状态分别记录 | 货源承诺 `emergency_commitments.status`（proposed/locked/shipped/released）、计算方案 `emergency_plans.status`（optimal/feasible/lower_bound/selected/locked/invalidated）、应急单 `emergency_orders.status`（awaiting_confirmation/confirmed/invalidated/cancelled） |
| 锁量 | 店长选货只生成「待确认」应急单并登记货源承诺；**区域负责人（总部）确认费用**后才从可供箱数扣减并锁定本次选货数量；原订单不变 |
| 输入修订 | 任何输入变化（供货减少 / 车辆晚到 / 优先级调整 / 部分到货）→ `input_revision` 自增，旧计算立即失效；迟到的搜索结果以旧修订号回传 → 409 `STALE_INPUT`，不覆盖新选择 |
| 部分到货 | 先抵扣对应缺口，其余保留待补；同一回执重复上报幂等，不再增加库存 |
| 取消 | 已发货（received_boxes > 0）的承诺保留 `shipped`，不直接释放；未发货承诺释放回可供箱数 |
| 排除规则 | 单位无法换算（每箱份数 ≤ 0）或到货晚于目标商品销售时段的货源被排除并写明原因 |

**组合搜索、资源占用核对与重算全部在浏览器完成**（`web/src/lib/emergencySolver.ts`），服务端只做输入修订号 / 可供箱数 / 排除标记的核对，以及记录状态，不返回任何预写推荐结果。

随附数据：`server/src/data/emergency-scenario.json`（少送比例、分时需求曲线、11 条货源登记、5 条供货/收货事件；不含推荐结果）。事件需在页面逐条「应用」才生效。

## 演示数据与推荐操作路径

空库启动自动写入：3 门店 × 8 SKU（叶菜/根茎，含 1 个无历史新品）、近 60 天截断观测样本（含售罄截断、断货标记缺失降级、盘点差异剔除三种形态）、朝阳门店昨日「建议→确认→复盘」完整闭环、三门店明日建议表首版。

1. **建议与订货**（`hq` 登录）：选「降温超出预报」重算 → 生成 v2，v1 标记「已修订」且内容不变；
2. 同页（`store1` 登录）：在最新版本上改量、选原因码 → 确认订单；若总部先修订会收到冲突提示并自动刷新；
3. **收市复盘**：选昨天到货日 → 查看按订单版本归因的实销/报损/缺货损失（基准：观测需求）；补录报损单（窗口内结转重算）、提交盘点（差异批次样本剔除）；
4. **需求还原**：查看支撑到货日预测的近 7 日截断观测样本（截断/降级/剔除标记）；
5. **应急订货**（`store1` 登录，到货日默认明天）：三门店明日订单均已确认 → 打开「应急订货」→ 点「计算方案」（分批搜索约 0.2 秒）→ 看到当前最好方案与「忽略共享限制时的最低成本」对照 → 调整某商品优先级后重算 → 选货生成待确认应急单 → 换 `hq` 登录确认费用锁量 → 应用「供货量减少」事件 → 旧方案失效、用旧修订号回传被拒 → 应用部分到货与重复回执 → 应用「原订单晚到」→ 提示取消应急单（已发货部分不释放）。

## API 概览

统一前缀 `/api`，除登录外均需 `Authorization: Bearer <token>`；冲突返回 `409 {error:{code,message,details}}`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/auth/login` | 登录 |
| GET | `/meta` | 门店/品类/SKU/成本参数/系统口径 |
| GET | `/samples` | 需求还原截断观测样本（门店+品类+日期区间） |
| GET | `/suggestions` | 建议表 + 版本列表 + 当前版本明细 + 已确认订单 |
| POST | `/suggestions/generate` | 生成/事件重算（总部）；幂等键并表；已确认则 409 |
| GET | `/suggestions/versions/:id` | 历史版本只读详情 |
| POST | `/versions/:id/confirm` | 门店确认（幂等键）；旧版本 409、重复确认幂等 |
| GET | `/orders` · POST `/orders/:id/review` | 订单查询 · 生成复盘（幂等） |
| GET | `/reviews` · POST `/reviews/:id/entry` | 复盘查询 · 录入当日实绩（还原+归因+样本回流） |
| GET/POST | `/waste-records` | 报损单（窗口内结转重算/过窗存档） |
| GET | `/emergency?storeId&arrivalDate` | 应急推演数据（原单、货源、回执、方案、应急单、事件） |
| POST | `/emergency/sources` | 登记货源（整箱规格/替代比例/到达时刻/重量/容积/成本），触发输入修订 |
| POST | `/emergency/priorities` | 调整商品优先级，触发输入修订 |
| POST | `/emergency/events/:key/apply` | 应用随附事件（供货减少/车辆晚到/部分到货/重复回执/原单晚到） |
| POST | `/emergency/plans` | 回传浏览器计算结果（核对输入修订号、可供箱数、排除标记） |
| POST | `/emergency/plans/:id/select` · `/emergency/orders/:id/confirm` · `/emergency/orders/:id/cancel` | 选货（待确认）· 区域负责人确认费用锁量 · 取消（已发货不释放） |
| GET/POST | `/stocktakes` | 盘点（以盘点为准、差异批次剔除训练样本） |
